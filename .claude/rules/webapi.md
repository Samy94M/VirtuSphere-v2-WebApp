Use `lib/db.php` for database access and keep secrets behind EnvBoot. New SQL must use prepared statements. New web output must use centralized CSP/security headers and correct escaping for HTML versus JSON.

- A repo function that rewrites a row set (DELETE followed by INSERT) wraps it in `repo_transaction()` itself instead of trusting its callers. The empty middle state must never be committed: another reader treats the missing rows as proof that they are gone. `repo_transaction()` is re-entrant, so callers may nest it; MySQL has no nested transactions and would answer a second `BEGIN` by committing the outer one.
- `repo_transaction()` is the only way `lib/` code opens a transaction. A raw `$db->begin_transaction()` there is a defect even while it works: the depth tracker cannot see it, so composing it with any `repo_transaction()` caller silently commits half a transaction. Sole exception: the single outermost request transaction in the machine-API entry scripts (`db_importMAC.php`, `mecm_packages.php`), which nothing nests; code inside those blocks must not call `repo_transaction()`-wrapped repos.
- `db_importMAC.php` requires `job_id` (ADR-0035) and validates it before opening its request transaction, rechecks the active job with `FOR UPDATE`, and performs phase-2 interface, VM-state, status-event and `result_json` writes as raw prepared statements in that one transaction. No `repo_transaction()`-wrapped helper may be called from the block.
- Connection tests and fetch failures return a `VIRTUSPHERE_INVENTORY_ERROR_*` category plus a redacted operator detail, never a finished sentence. The portal maps the category through `connection_error_message()` and renders the detail behind the alert's `<details>`.
- Distinguish portal HTML from machine/API JSON. Portal errors are localized and HTML-escaped; machine/API responses keep their wire shape and use `json_encode`.
- Do not localize MECM, Ansible or deploy-worker response fields as part of portal language work.
- Shared helpers that emit user-facing portal strings should use `__t()` with a safe fallback if they can also run before the portal bootstrap.
- A module reachable from a CLI entrypoint requires every `lib/` file whose functions it calls. A portal page may call `h()` or `__t()` without requiring `lib/layout.php`, because the bootstrap loaded it; a worker has no bootstrap, so its require closure is all there is. `lib/deploy_worker_outcome.php` called `repo_record_worker_result()` without requiring `lib/repo/heartbeats.php`: the deploy worker never wrote its System status row, and the page told the operator to restart a worker that was up and processing jobs. It stayed invisible because the report is wrapped in `catch (Throwable)` and `Error` is one, so the fatal decayed into an STDERR line per minute, and because the test that covers the row requires `lib/maintenance_tasks.php`, which pulls the module in and made the broken entry point green. A `catch (Throwable)` guarding a side channel (a status row, an audit line) must therefore never be the only thing standing between a coding error and production; `tests/Static/CliRequireClosureContractTest.php` walks the closures, and a call that is source-reachable but CLI-unreachable goes in its `GUARDED` with the guard that makes it so. Which files it walks is derived, never listed: the top-level `if (PHP_SAPI !== 'cli')` guard an entrypoint carries is the marker, `DUAL_SAPI` holds the one file that serves both SAPIs on purpose (`lib/migrate.php`), and a second scan over the project's own compose commands, healthchecks and setup scripts proves that registry complete from the outside. The hand-written predecessor claimed "every CLI entrypoint" while missing `lib/seed.php`, and walking it found a real gap in `lib/repo/log.php`. A new CLI entrypoint therefore needs no test edit; a new *invocation* of a file that is neither guarded nor registered fails the build.
- Keep logs and operator diagnostics detailed, but map them to safe user-facing messages before rendering in the portal.
- A failure detector must not count silence it was not awake to observe, and its verdict must name what was established, not what was assumed. While the database was unreachable nothing could write a heartbeat, so the moment it returns every running job looks abandoned and `repo_reap_stale_deploy_jobs()` cannot tell a dead worker from its own blind spot: it failed a healthy job whose playbook then kept running against ESXi under a terminal row. A process therefore records when its CURRENT connection was established (`deploy_reap_observer_since()`, set on connect AND on every reconnect) and waits out `VIRTUSPHERE_DEPLOY_REAP_OBSERVER_GRACE_SECONDS` before reaping; the gate sits inside `deploy_worker_reap_stale_jobs()` where no caller can forget it, and an unset observer counts as blind. This costs nothing where it matters: an observer connected all along was never blind and reaps a genuinely dead worker with no delay. One consequence is a tool contract, not an accident: `deploy_worker.php --once` connects and reaps immediately, so it is always inside its own grace and never reaps; forcing it would need its own named operator switch. The message then states only what the transaction can see, through the one pure wording `deploy_job_reap_observation()` (job id, heartbeat age against the limit, `locked_by`, transition), because "no heartbeat for N seconds" is the mechanism that noticed, not what happened, and it implied one instruction ("restart the service") that was as likely wrong as right. A caller may append a further OBSERVATION labelled as separate (`integration_deploy_worker_alive_now()`), never a cause: a singleton status row identifies no process, and a restart writes a fresh one, so "reporting" does not establish that this job's owner survived. Never assert a cause a code path did not check: the VM convergence note said "the worker died before confirming" on a path also reached with the worker alive.
- A side channel must not end the work it only describes. A job log line and a job heartbeat are not the deploy: the playbook runs on the Ansible host and keeps changing ESXi whether or not this process can reach MySQL, so the first `mysqli_sql_exception` from a stream logger propagating out of an SSH callback aborted the transport and the job was then classified as a *transport* failure, i.e. a database restart read as "the Ansible host answered unexpectedly" while the remote exit code, the only remaining evidence about the VMs already created, was thrown away. Every database write of a running job therefore goes through `DeployWorkerDbChannel` (`lib/deploy_worker_db_channel.php`), which OWNS the connection: callers ask it for the live handle at each use (`$channel->connection()`) and never capture a `mysqli`, because after a reconnect a captured handle is a dead object that keeps throwing. An outage is announced exactly once on STDERR, redacted; finished, already redacted log lines wait in a bounded FIFO whose overflow is reported by its own SYSTEM line, since an unbounded spool turns a database restart into an OOM kill and silent dropping turns it into a job log that lies; and a tick attempts at most one backed-off reconnect, because a retry loop inside a stream callback stops reading the very SSH channel this exists to protect. After a reconnect the order is fixed: ownership, then heartbeat, then spool. A job whose ownership is gone stops WITHOUT publishing a result. The DB operations sit behind the injectable `DeployWorkerDbOperations` seam (`lib/deploy_worker_db_operations.php`) because a real `mysqli` cannot be made to fail on cue; `DeployWorkerDbChannelTest` drives every branch with no database and no real backoff, and `DeployWorkerDbChannelRecoveryTest` proves the replay and the ownership recheck against the server.
- The free-text `os_status`/`package_status` columns are normalized on write: the repo validators run `catalog_normalize_status()` (`lib/repo/catalog.php`), which folds known synonyms onto the canonical `Aktiv`/`Retired` and passes unknown text through. Any new write path for these columns routes through the validators, not a raw INSERT/UPDATE.
- Detect a template by its name with `mission_name_is_template()` (`lib/defaults.php`), never an inline `str_starts_with($name, VIRTUSPHERE_TEMPLATE_PREFIX)`; the helper trims to match stored names.- What a stored job-log line may look like is decided in ONE place, before it can reach the database or the outage spool: `DeployJobOutputGate` (`lib/deploy_job_output.php`), which `DeployWorkerDbChannel::log()` runs for every line. It enforces valid UTF-8, strips ANSI and the other control sequences with a deliberately allowed tab, redacts the job's secrets in plain and URL-encoded form, and caps line size and per-job volume, writing exactly one SYSTEM sentence per truncation kind. Two orderings are load-bearing and neither is cosmetic: normalisation runs BEFORE redaction, because a colour sequence in the middle of a value defeats a plain `str_replace`; and the whole gate runs BEFORE the spool, because an outage that parks an unredacted line means a later drain persists a secret. A caller must therefore not normalise or redact a log line itself, and a reader must not "clean up" on display; three readers (portal table, polling JSON, raw download) would be three rules that drift. A reached limit never ends the run: the playbook keeps changing ESXi and the heartbeat keeps beating, so only the diagnosis is marked as cut. The stored source is `ansible` (merged remote output, because the remote command redirects with `2>&1`), `worker_error` (this worker's finding) or `system` (this worker's own step); `stdout`/`stderr` are legacy values that stay readable and render through `deploy_job_log_source_label()` as the same Ansible output, because they never were two channels and a UI must not offer to separate them.
- A remote sequence is one command per step, never one `a && b` chain. A chain has no boundary the portal can stand on: while it ran, an accepted cancel could only be honoured after the LAST playbook, so ADR-0033 and the deploy help promised a stop the worker could not perform. `ansible_remote_steps()` (`lib/ansible_command_modes.php`) yields ordered descriptors, and `deploy_worker_assert_job_is_ours()` decides before each and after each finished step whether a next one starts. The promise that follows is exact and belongs in every text about it: the running step may carry out its changes on ESXi completely, and no further step starts afterwards. Finalisation is a compare-and-swap out of `running` under this worker's lock; when it hits zero rows the row is re-read rather than guessed, and a `cancelling` job under our own lock is confirmed `cancelled` right there, because nobody else is going to conclude a job this worker still holds. One consequence is a cleanup contract: an `EXIT` trap is impossible per step (it would delete the job directory after the first playbook), so each step traps HUP/INT/TERM and the worker removes the directory itself after a sequence ENDED. A step that never returned is deliberately left alone and said so in the log; deleting under a running playbook would destroy the work whose outcome is still unknown.
- An uploaded document that a preview reports on and a write persists is canonicalized ONCE, before either reads it. The mission import read the same file twice in two ways: the report counted `(array) ($vm['interfaces'] ?? [])` while the transaction projected `VIRTUSPHERE_MISSION_TRANSFER_INTERFACE_FIELDS`, so `interfaces: "oops"` counted as one interface and produced no finding while the write would have built an empty DHCP interface, `disks: "oops"` counted as one disk and wrote none, and a foreign `interfaces[*].mac` blocked a preview over a value the import deliberately drops. A cast never fails, so nothing noticed. `mission_transfer_document_analyze()` (`lib/mission_transfer_document.php`) is the one reading: container shape decided by `array_is_list()` and never by a cast, only the declared field lists projected, every rejected shape reported with its position, and anything outside those lists unknown in BOTH directions, so it can neither block nor be written. Counts come from canonical entries alone, which is what makes a count in an unblocked report a promise about the write. A repo list validator that throws at the first bad entry is re-run per entry to collect the rest (`mission_import_list_field_errors()`), but only AFTER the whole list ran through its owner, so a future list-wide rule keeps its one home; no rule is ever copied out of the repo layer.
- A session hand-off is deleted only by the request that owns it. The mission import preview kept its token/TTL condition in two places, and the copy in the GET path answered a token MISMATCH with `unset($_SESSION[...])`: opening the stale link of upload A destroyed the still valid preview of upload B in the same session. One pure predicate answers both paths with a closed status (`mission_import_handoff_status()`, `valid | expired | mismatch | missing | invalid`); it cannot delete anything, and only `expired`, `invalid` and a completed action may clear the state. The TTL boundary is inclusive, a status the request does not own says only what is established ("nothing behind this link"), never "expired", and a provably dead state may be swept silently on any later render. Every terminal status is pinned to its own visible exit and its own deletion rule by `MissionImportPreviewErrorContractTest`, because counting flashes over the whole block leaves a new silent branch green behind the older ones.
- An expected operator-side failure is localized and logs nothing; an unexpected caught fault gets an error reference plus exactly one safe server line. `mission_import_diagnose()` (`lib/mission_import_portal.php`) takes a scope from a closed list and either a Throwable (class name only, never its message) or an upload code, so there is no parameter a payload, token, file name or temp path could enter through. It writes through `error_log()` to the configured PHP error log, not `repo_log_failure()` and not an audit row: `deploy_logs` answers successful functional changes and security events, and a second diagnostic channel for one fault means neither is complete. Classify every `UPLOAD_ERR_*` code separately rather than folding them into "no file chosen" (a file rejected by `upload_max_filesize` told the operator they had picked nothing, so they picked it again). A `MAX_FILE_SIZE` hidden field is PHP-side early detection only and never a boundary: the server compares the reported size against the same constant, and `MissionImportUploadLimitContractTest` pins app limit < `upload_max_filesize` < `post_max_size` < nginx `client_max_body_size` plus equality of the two nginx sources. Above `post_max_size` PHP sees neither action nor CSRF token nor payload, so no localized answer is possible there at all; say that in the runbook instead of promising one.
