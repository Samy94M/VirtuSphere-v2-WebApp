A playbook filename is a contract with `VIRTUSPHERE_PLAYBOOKS` and `VIRTUSPHERE_CREATE_*` in `lib/defaults.php`/`lib/deploy_create_constants.php`, not a free choice; renaming one without both sides is a job that dies on the host with "could not be found". `upload_mac_list.py` must stay air-gap friendly and use Python stdlib HTTP, not `requests`, after its migration.

The create path is four control playbooks driven by the worker, one VM at a time (ADR-0041), plus the shared `create_identity_check_tasks.yml` and `emit_create_result.py`. Rules that are load-bearing rather than stylistic: `createVMLaunch` starts exactly ONE `vmware_guest` call with `async` and `poll: 0` and never loops a selection; `createVMStatus` decides on the presence of the async status file and not on the module's `finished`/`failed`, because `async_status` answers a vanished job id with `finished: true` and no failure; the only machine-readable channel is one `::virtusphere-create:: v1 <base64url>` line per control call, and a missing, doubled, oversized or contradictory marker is a protocol error that must never be reconstructed from ordinary Ansible lines; an identity conflict is a closed FACT (`vs_identity_conflict`, its code and reason) reported as a `rejected` marker, never an aborted call, because a foreign namesake is the most common real case and an unmarked abort reaches the worker as a broken transport. Every artifact the worker dispatches must be listed in `VIRTUSPHERE_CREATE_ARTIFACTS`, and shared task files stay FLAT: the SFTP upload copies only the top level of the work directory and drops a subdirectory silently.

A task under `ignore_errors: true` must be verified against its module's argument spec, and its outcome must reach the marker the PHP side reads. Tolerated failure plus an unchecked argument list is a task that can never succeed while looking like a host that has nothing: `vmware_portgroup_info` requires one of `cluster_name`/`esxi_hostname` and `vmware_dvs_portgroup_info` requires `datacenter`; neither was passed, so the portal reported 0 portgroups for a host with thirteen and no error said otherwise. The pinned collection answers the question directly, without an ESXi host: `docker run --rm virtusphere-qa-ansible:latest ansible-playbook <a task calling the module with dummy credentials>` fails on argument validation before it opens a connection. `AnsiblePlaybookHygieneContractTest` pins both the required arguments and that every registered task appears in the `queries` block.
