## R2 Server and client logging are separate runtime modules with one mirrored contract: mecm/VirtuSp

Server and client logging are separate runtime modules with one mirrored contract: `mecm/VirtuSphere-Logging.ps1` and `clients/VirtuSphere-Client-Logging.ps1`. Keep version, levels, six-field schema, daily filename, UTF-8 byte bounds, redaction, 30-day retention and 24-hour cleanup cadence in parity, then extend `VirtuSphere.Logging.Tests.ps1`. Common facades must fail visibly for a missing or version-mismatched adjacent module. The MECM server scripts likewise declare their required Common contract; the installer compares the staged and activated literals, and a long-running script checks the loaded contract before doing work. Any installer or packaging change carries phase/script, Common and logging module as a staged SHA-256-checked set and proves both fresh install and upgrade. A file-sink failure may warn locally once per outage and once on recovery, but must never stop the business action, recurse into logging, send extra heartbeat/report traffic or create audit spam. Correlation remains an additive diagnostic header; do not change a machine endpoint JSON body to carry it.

Package-wrapper reporting has a separate inactive-until-enabled delivery set. `clients/VirtuSphere-Client-Common.ps1`, `VirtuSphere-Client-Logging.ps1`, `VirtuSphere-Package-Reporter.ps1` and `VirtuSphere-Package-ReporterHost.ps1` are its only source owners. The MECM installer derives an immutable `reporting/<sha256>/` generation and complete manifest from those files, binds it to the staged wrapper hash and publishes `reporting/current.json` last. The autoimporter hashes the complete template tree and synchronizes only the wrapper plus the selected reporting generation; it never overwrites package `config.json` or `powershell/`. Existing content-addressed generations are retained until a safe active-reader cleanup contract exists. A missing, mixed or damaged set is an open `package_template_failed` warning and must not alter package execution. Do not commit generated reporter copies under `Package_Vorlage` or return to a one-file template stamp.

`Package_Vorlage/install.ps1` owns a deliberately smaller local run logger and does not import the daily server/client logger. After valid package identity and log-root selection, but before registry mutation, it creates independent `wrapper_` and `reporting_` UTF-8-BOM sinks with one UTC/GUID stem under `PackageWrapper/<identity-sha256>`. The identity hash is the SHA-256 of the length-prefixed UTF-8 bytes of exact `ProjectName` and version. Each sink uses CreateNew, immediate flush and FileShare.Read; one sink failure is non-fatal to the other sink and package business result. Wrapper events observe the existing result owner: stable inventory, RUN before hash evaluation, exactly one OK/SKIP/FAIL per processed step, monotonic durations and one best-effort completion with detection status. Never infer child execution for SKIP, copy child output, serialize config/exceptions, or let logging alter Stop/Continue, 1641/3010 or detection behavior.

Local retention counts exact run stems, not files. It protects the newest five groups plus the current run, only considers direct regular files matching the owned name grammar, rejects reparse points and broadly writable managed directories, and opens every partner with write access before deletion so an active writer that shares read-only protects the whole group. A locked or unsafe group is skipped, so five is a retention target rather than a hard storage cap. Deletion is literal, non-recursive and non-atomic across partners. Transport remains separately disabled until the supervised reporter/time-budget contract is activated; the reporting sink records that local reason and is never an outbox or replay source.

## R3 An error path needs a counter and a cause, and a success sentence needs a condition. A caught e

An error path needs a counter and a cause, and a success sentence needs a condition. A caught error that only writes a log line never reaches the run report, so the loop answers `ok` while the collection sits in the wrong folder; every `catch` in the four loops either raises a reported counter (`$dataWarnings`, `$itemFailures`, `$scanWarnings`, `$targetsSkipped`) with an `Add-VsRunCause` code from the closed vocabulary, or rethrows. The same rule one level up: a green closing line must read the outcome, not the last step. Both installers said "bereit" unconditionally, so four running tasks plus a portal answering 403 was a green first install, and the 403 was that script's own next-step item 1. `$script:VsInstallBlockers` counts blockers only; `Write-Warn` counts, `Write-Hint` does not, and the choice sits at the call site rather than in a central list so that a new warning forces a decision and a test can see it (`ErrorPaths`). A run that leaves something unhealed must not stamp it as done, and must not report a number nobody set: a state that is not fixed stays in the queue. The autoimporter deliberately separates that open warning from deployment and retirement readiness: a confirmed content request permits idempotent collection/deployment reconciliation even with zero successful DPs. `removeOldVersion=true` authorizes automatic retirement once that request is bound to the exact replacement content, safe target evidence and the deployment are proven; incomplete DP copies do not veto it. The versioned plan includes old deployments, applications and collections in that removal order, requires ownership and complete reference evidence, and must hash-identically after an immediate second read. Full DP copy evidence still gates only the manifest stamp and the claim that distribution is complete. Missing prerequisites, unconfirmed calls, identity/projection uncertainty, target loss and DP removal states remain fail-closed before those mutations.

## R4 A task must report the value it acts on, and both must be the same expression. Three of the fou

A task must report the value it acts on, and both must be the same expression. Three of the four scripts clamped their configured interval only upward (`[Math]::Max(30, …)`) while `Send-VsRunReport` clamps both ends: a registry value above the wire maximum made the task sleep longer than the number it sent, and the System status page derives its colour from the number it *received*, so the row sat on "Verzögert" forever while the task did exactly what it was configured to do. `Resolve-VsInterval` (`VirtuSphere-Common.ps1`) resolves it once for the sleep and the report; the per-task floors live in `$script:VsIntervalBounds`, which `install-VirtuSphere-MECM.ps1` mirrors in `ValidateRange` and `VirtuSphere.RunReport.Tests.ps1` pins in both directions. Clamping is never silent: a corrected setting writes a WARN line, because a value that quietly changes is the same defect one turn earlier. A setting the operator can tune must also survive a re-run of the installer that did not name it, or a script update resets it and the page reports the new cadence as fact.

## R5 The MECM device cache is three multimaps (ResourceID, normalised name, every normalised MAC), n

The MECM device cache is three multimaps (ResourceID, normalised name, every normalised MAC), never a hash keyed on the display name. `$mecmDevices[$d.Name] = $d` resolved duplicates silently by last-wins, and which of two identically named records won was decided by the order of the provider's answer; an ambiguity has to stay an error instead of becoming a selection heuristic. `Resolve-VsDeviceIdentity` is pure so Pester can drive every branch without MECM, and the order in it is the statement: a bound ResourceID decides alone and a DIFFERING display name is explicitly not a finding (Windows and Discovery are supposed to rename it), while a missing ResourceID or a foreign MAC blocks rather than adopting a similarly named replacement. Identity is resolved BEFORE any membership mutation, because a rule added to the wrong ResourceID cannot be taken back by anyone who does not know it happened. After an import nothing is inferred from the error text: name and MAC are read uniquely again, and `-MergeIfExist` and a name-only fallback are not conflict resolutions. A PowerShell hashtable miss yields `$null`, and `@($null)` has Count 1, so every lookup goes through `Get-VsIndexHits`; the plain form made an unknown name plus an unknown MAC look like two hits with the same empty ResourceID and answered `use` instead of `import`. `ConvertTo-VsHostnameKey` mirrors `mecm_hostname_key()` exactly and uses `ToLowerInvariant`, because a Turkish locale would otherwise make `BACKUP-1` a different machine on this server than on any other.
