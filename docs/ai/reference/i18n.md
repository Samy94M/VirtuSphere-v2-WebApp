## R4 Keys use the Lager-style module.key convention through __t('module.key'). The module is the cat

- Keys use the Lager-style `module.key` convention through `__t('module.key')`. The module is the catalog filename, so splitting a catalog that outgrew the 400-line budget renames every key it holds: cut along a renderer that already has its own file (`lib/help/system_status.php` owns `lang/{de,en}/help_system_status.php`), move both locales in one step, and re-render the page to check for keys echoing themselves. Watch for keys a renderer builds at runtime (`__t('help_system_status.esxi_cause_fix_' . $code)`); a grep for literals will not find them. A list numbered in the catalog (`<prefix>1` to `<prefix>n`) loops to `Lang::countNumbered('<module>.<prefix>')`, never to a count written into the template: the help loop over `system_status_identity_1` to `_9` was fixed at 9, and a tenth key would have stayed unrendered without any test noticing (`LangCatalogTest` pins the derivation). A structure with several numberings follows the same rule: the stack FAQ reads questions, paragraphs and list items from the catalog through `help_stack_faq()` (`lib/help_page.php`) instead of a written table of counts; only the list kind (`VIRTUSPHERE_HELP_STACK_FAQ_ORDERED_LISTS`) is declared, because the keys cannot say it. `HelpStackFaqTest` requires every `stack_q`/`stack_a` key of both locales to render exactly once and proves with synthetic catalogs that a gap or an answer without its question is caught.

## R5 A test that scans catalogs must glob them per locale (lang/<locale>/help*.php), never list file

- A test that scans catalogs must glob them per locale (`lang/<locale>/help*.php`), never list filenames. `InventoryQueryVocabularyContractTest` listed `lang/de/help.php` and went red the moment the catalog was split, for a vocabulary that had not moved out of the help at all: which module holds a sentence is a layout decision, "the help teaches this word" is the contract. The rule covers the browser layer too: `health-matrix.spec.js` derives its key prefixes from the catalog filenames (`fs.readdirSync` over `lang/de/`) and fails when the derivation comes back empty, because an empty prefix list makes its regex unsatisfiable and the check permanently, silently green. Its hardcoded predecessor had lost four catalogs, `help_system_status` among them, whose keys `help.php` renders. That spec scans only the locale the browser negotiates; the other one is covered by the parity audit, not by a second pass.

## R8 No em dash (—) in user-facing prose (help, hints, explanations, flash messages) in either local

- No em dash (`—`) in user-facing prose (help, hints, explanations, flash messages) in either locale; use colon, semicolon, comma or a new sentence instead. The em dash is only allowed as an empty-value placeholder in table cells.
- `scripts/lang-audit.php` (gate `lang-parity`) enforces this for every catalog value in `lang/{de,en}/*.php` as `[lang-audit.sentence-dash]`: `—` (U+2014) anywhere, `–` (U+2013) everywhere except directly between two digits (a range). A value that is only the dash is the placeholder and stays allowed; text inside `<code>…</code>` or `<pre>…</pre>` is a literal, as in R11. Guard-harness cases `lang-audit.sentence-dash`, `lang-audit.sentence-dash-en-dash` and `lang-audit.sentence-dash-allowed`. Tests for single keys do not repeat this check.

## R14 German catalog values write real umlauts

- A value in `lang/de/*.php` writes `ä`, `ö`, `ü` and `ß`, never `ae`, `oe`, `ue` or `ss` in their place. `scripts/lang-audit.php` reports a replacement spelling as `[lang-audit.umlaut-spelling]` from a short list of stems (`ueber`, `koenn`, `loesch`, `schluessel`, …; `fuer` only as a whole word) and for any word that starts with `ue`/`Ue` before a lower-case letter (`uebrig`; case-sensitive, so `UEFI` stays clean). A stem goes on the list only if no real word contains it, so `aktuell`, `neue`, `Quelle` or `Queue` never hit (harness case `lang-audit.umlaut-clean`; the red cases are `lang-audit.umlaut-spelling`, `lang-audit.umlaut-spelling-stem` and `lang-audit.umlaut-word-start`). The list is a net for the typical slips, not a dictionary: a new frequent slip extends the list together with a probe word that must stay clean. Same literal exemption as R11. An empty locale catalog is `[lang-audit.zero-match]` (harness case `lang-audit.zero-match`), so no rule can pass on nothing.

## R9 Never write out a number a constant owns (a limit, timeout, interval, threshold, retention wind

- Never write out a number a constant owns (a limit, timeout, interval, threshold, retention window). Put a placeholder in the text and pass the constant at the call site, in both locales. A hardcoded number keeps working while it quietly starts lying, which is why `scripts/check-bounds-sync.php` fails the build on one; a number the project genuinely does not own (the NetBIOS 15, a VARCHAR width) goes in that script's `BOUNDS_EXEMPT` with its reason. Placeholders must match across DE and EN, or one locale silently drops the number. `Lang::replace()` fills them in one pass, longest name first, so `:page` and `:pages` may share a text and a filled-in value is never searched again.
- The same holds for a list of deploy modes in a sentence ("only in the modes ..."): pass `deploy_mode_label_list()` from `lib/deploy_mode_labels.php` over the constant or predicate that decides the behaviour (`VIRTUSPHERE_DEPLOY_STAGGER_MODES`, `deploy_mode_requires_wds_ready()`, `ansible_modes_using_start()`, ...), and name a single mode only by its `status.mode_*` display label. This focused module loads its language and predicate owners and is shared by portal views and input validation without importing badge renderers into CLI paths. `virtusphere_deploy_mode_labels()` is the technical validation set and never visible text. `DeployModeTextTest` derives every list and fails on a hand-written mode name or a technical label that differs from the localized one.

## R10 Audit log sentences are rendered per viewer locale from the structured row, not translated in storage

- Audit log sentences live in `lang/{de,en}/audit_log.php`; the logs page renders a structured row in the viewer's locale (`audit_log_display()`, `lib/audit_log_view.php`), while the stored `log_message` stays English and canonical because the writers call the presenter with `'en'` and search, the CSV export and the saved filters read it.
- A closed word in the context (a reason, an outcome, a state, a blocker, a mode) goes through `audit_code_label($locale, '<field>', $word)` (`lib/audit_presenter_parts.php`), key `code_<field>_<slug>` in `audit_log`. The English value is the word itself, so the stored sentence keeps it byte for byte; the German value is the display word, and a mode's German word is its `status.mode_*` label (R9). An unknown word (a legacy row, free text) shows as written. Every list has one owner: new words without a constant live in `lib/audit_vocabulary.php`, and `audit_code_vocabularies()` (`lib/audit_vocabulary_lists.php`, loaded by tests and tools only) references the existing lists. Writers pass the constant, never a typed literal. `AuditCodeVocabularyContractTest` derives the lists, the presenter fields and the writer calls and demands a label in both locales; names, hosts, IDs and setting values stay as written. The user role of a role change is such a closed word (`code_user_role_*`, German word = `layout.role_*`; P3-6, TS1-K3).
- A fixed identifier a sentence names that is no context word (the setting key of `settings.changed`, the log tab of an export, the retention areas of a purge; P3-6, P3-10) goes through `audit_identifier_label($locale, '<kind>', $identifier, $stored)` (`lib/audit_presenter_parts.php`), key `ident_<kind>_<identifier>`. The English value is the form the stored sentence has always written (`session lifetime minutes`, `security`, `job_log_lines`), so the stored sentence stays byte for byte; an unknown identifier shows its stored form. `AuditIdentifierLabelTest` derives the setting keys from the settings writers, the tabs from `VIRTUSPHERE_LOG_TABS` and the areas from the retention job, and pins the German tab word to `logs.tab_*`.

## R11 German catalog values quote with the German pair „…“ only

- A value in `lang/de/*.php` quotes with `„` (U+201E) and closes with `“` (U+201C). A straight ASCII `"`, an English closing `”` (U+201D), an unclosed pair, a closing mark without an opening one and a second opening mark inside an open pair are findings of `[lang-audit.quote-mix]` in `scripts/lang-audit.php` (gate `lang-parity`, guard-harness cases `lang-audit.quote-mix` and `lang-audit.quote-unclosed`). Text inside `<code>…</code>` or `<pre>…</pre>` is a literal and is not checked; PHP comments never reach the check because it reads the loaded values. The English form is R12.

## R12 English catalog values quote with the straight pair "…" only

- A value in `lang/en/*.php` quotes with the straight ASCII pair `"…"` and writes the apostrophe as a straight `'`. A typographic `“` `”` `‘` `’`, a German `„` `‚` or a French `«` `»` is a finding of `[lang-audit.quote-mix]` (detail `en: typographic quote mark U+…`), and so is an odd number of straight `"` in a value (detail `en: straight quote " is never closed`); guard-harness cases `lang-audit.quote-en-typographic` and `lang-audit.quote-en-unclosed`. Same literal exemption as R11 for `<code>…</code>` and `<pre>…</pre>`.
- Why straight: many English quotes cite a value the portal or the job log prints verbatim, or that an operator types (`"skipped"`, `":host"`, a command), and the catalog was already 86 % straight. The output stays escaped by `h()` in HTML and attributes and by `json_encode()` in payloads, so a straight quote needs no other treatment.
- Tests that pin English wording with quotes (`InventoryQueryVocabularyContractTest`, `tests/e2e/specs/work-context.spec.js`) already used the straight form; the visual targets render German and are not affected.

## R13 Stored English diagnostic texts stay English and are shown only as technical details

- `deploy_create_vm_results.error_detail`/`first_error_detail` and `deploy_jobs.terminal_reason_detail` are English diagnostic texts written by the worker (and, for a module failure, the host's own message). They are stored and transported as written, never translated, and never parsed for a decision. A person reads the closed, localized sentence of the code (`VIRTUSPHERE_CREATE_ERROR_REASON_KEYS` in `lib/deploy_create_progress_findings.php`, `deploy.terminal_reason_*`); the stored text appears verbatim only inside `<code>` in the collapsed "Technische Details" (`lib/deploy_log_outcome.php`), for a module failure under the label "Meldung des Hosts" and for a protocol error with a printed cause under "Letzte Fehlerzeile von Ansible". The result block, the progress card and its live payload carry the sentence alone: on the first look "503 Service Unavailable" read as a different problem (user decision 29.10.2026). The host label depends on the origin the worker recorded (`error_detail_from_host`, migration 0067), never on comparing the text: a fallback reads "Der Host hat keine genauere Meldung geliefert.", an unrecorded origin "Gespeicherter Text:". Every stored create error code has its sentence in both locales (`CreateErrorReasonContractTest`).
