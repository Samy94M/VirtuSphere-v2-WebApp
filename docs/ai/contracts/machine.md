## A55 getDeviceList uses the pinned VIRTUSPHERE_MECM_DEVICE_LIST_COLUMNS projection, never SELECT *;

- `getDeviceList` uses the pinned `VIRTUSPHERE_MECM_DEVICE_LIST_COLUMNS` projection, never `SELECT *`; on the wire `vm_name` is the ESXi identity and `vm_hostname` is the frozen rollout snapshot. Every mutating MECM/client callback carries `rollout_revision` and is fenced inside one transaction with its write (ADR-0043). `transfer_generation` (additive, AV-P0) is the queueing counter of the row; the MAC callback increments it with `updated = 1` for each successful unbound VM, while the bound-VM comparison path stays unchanged. `updateDevice` may report it back, and the portal clears `updated` only when the reported value equals the stored one, in the binding write and in the `noop` duplicate alike. A callback without it clears whatever is queued (the behaviour before the counter); a present value that is not a non-negative integer is 400. The column `mecm_sync_state` carries the stored value except for the deploy failure mark: stored `deploy_failed` (migration 0070) stays `failed` on the wire through `virtusphere_mecm_sync_wire_value()` (ADR-0019 amendment 5); a wire alias never collides with a stored value.

## A62 mecm-api.php: read surface with getDeviceList and the minimal, side-effect-free getDeviceInfos&

- `mecm-api.php`: read surface with `getDeviceList` and the minimal, side-effect-free `getDeviceInfos&mac=...`; `getMissionName` was retired by ADR-0019. The bootstrap payload additively includes ADR-0044 `device_generation` and `acceptance_generation`, both canonical lowercase UUIDs, so the package reporter can carry its VM-incarnation and post-restore fences. Additive `disks` (DN1, ADR-0019 amendment 6) lists the disk layout in serverlist order, `{position, scsi_unit, size_gb, volume_label}` from `vm_disk_client_layout()` (`lib/vm_disk_layout.php`, sole owner of rows, SCSI unit rule and label rule, `VIRTUSPHERE_DISK_VOLUME_LABEL_MAX` mirrored by `$volumeLabelMax` in `client_VMDisksOnline.ps1`). Only that disk phase reads it, and only for NEW data disks; an uncertain match keeps `VM_Disk_<n>` with a closed reason and never fails the phase or renames an existing volume.

## A66 db_importMAC.php: Ansible MAC import; payload { "mission_id": 123, "job_id": 45, "results": [..

- `db_importMAC.php`: Ansible MAC import; payload `{ "mission_id": 123, "job_id": 45, "results": [...] }`, `job_id` required (ADR-0035). New writes use strict result V2 with per-VM exact WDS evidence and semantic callback fingerprint; historical V1 remains readable. The request/result/response bounds are centralized in `lib/mac_import_constants.php`, and callback fencing must preserve the existing endpoint envelope and HTTP meanings.
- WM-E1: a stored nonempty ResourceID makes export a MAC comparison. Equal MACs preserve the entire VM/interface state and return the existing V2 `success` row with `updated_interfaces=0`; the portal calls it unchanged. A changed mapped MAC returns `bound_mac_changed`, preserves MACs and ResourceID, and is failed by the existing worker conclusion. Its retry is blocked as an identity finding while the VM stays bound and its stored MAC still differs from the reported one (K24, the same `virtusphere_bound_mac_conflict()` predicate, evaluated against current state); a MECM-ID reset or a MAC correction lifts the block. An empty stored MAC on a bound VM is "not known yet" (K3 decision (b)): the callback writes only those MACs, keeps every VM state field, counts them in `updated_interfaces` and records a fixed system line in the job log in the same transaction; the portal derives its "first MAC" notice from that line. Comparison is on normalized MACs. There is no new response field, outcome token or result version.
- K15 changes only incomplete-job VM-state convergence: Export first records an admitted attempt for each VM before `guest_info`; failure, cancellation, reaper and sweep apply the same per-VM journal decision. Successful imported VM IDs remain protected. This does not change the callback envelope, outcome tokens or V2 fingerprint.

## A67 mecm_report.php: report channel (ADR-0018/ADR-0044), POST-only

- `mecm_report.php`: report channel, POST-only. The existing `reportPhase`, `heartbeat` and `reportRun` contracts remain as defined by ADR-0018; the optional `X-VirtuSphere-Token` applies only to `heartbeat`, `reportRun` and `reportDeviceCauses`. `reportRun.script_version` stays optional free text of at most 32 characters. The MECM server tasks send `<task>/<x.y>+<release>` with the release `JJJJ.MM.N` (N 1 to 99), or the older `+<commit7>`, `+unbekannt`, `+ohne-manifest`, each optionally followed by `-abw`; the portal parses it only for the settings tab "Version" and never rejects a report because of it. The sync error categories are the closed list `VIRTUSPHERE_RUN_SYNC_ERROR_CATEGORIES` (mirror `$script:VsRunSyncErrorCategories` in `VirtuSphere-Common.ps1`, pinned by `RunReport.Tests.ps1` and `RunReportValidateTest`); `journal_blocked`, `portal_rejected` and `source_changing` are accepted since 17.10.2026, portal first, and the server scripts of release 2026.10.1 send them (Block 2a); a MECM server still on older scripts keeps reporting `portal_unreachable` or `mecm_unavailable` for those cases. The autoimporter's `detail` cause codes `package_content_group_empty` and `package_folder_failed` follow the same order: accepted and labelled by the portal since 20.10.2026, sent by the server scripts of release 2026.10.1. AV2 (ADR-0034 Amendment 7) adds `package_content_request_failed` (no DP group or a content call MECM did not accept); the portal labels it in the same release whose server scripts (`autoimporter/2.3`) send it. Since then `package_content_failed` and `package_content_in_progress` are distribution hints: they may appear in the `detail` of an `ok` run, and the portal shows them without changing the outcome. Additive `reportPackageRun` is the ADR-0044 package-wrapper channel: IP-allowlist only, strict V1 JSON up to 64 KiB, unique MAC-set resolution, rollout/device/restore-generation fences and transactional replay semantics. Its successful response repeats `schema_version`, `run_id`, `event` and `event_seq` plus exact `accepted`/`deduplicated` booleans. It never changes VM lifecycle, integration heartbeat state or package catalog state and emits no per-report audit event.
- `reportRun.site_parts` (MSB, ADR-0018 amendment 2026-11-09) is an optional top-level object, only on a completed `mecm-site-health` report: `roles` and `components` as lists of `{name, status, count}` (status 1 or 2, at most `VIRTUSPHERE_SITE_PART_MAX_ENTRIES` each, names only from `VIRTUSPHERE_SITE_PART_NAME_PATTERN`) plus `omitted`. Never a summary key, so an older portal ignores it instead of refusing the report; this portal refuses a malformed object or one from another source with 400 `Invalid site_parts`. The outcome/category binding is unchanged; the reporter sends counts by type only, never server names or MECM messages, and the portal alone classifies the types (`lib/mecm_site_assessment.php`). Mirror: `$script:VsSitePart*` in `VirtuSphere-Common.ps1`, pinned by `VirtuSphere.SiteParts.Tests.ps1`.
- Additive `reportDeviceCauses` (MX1, ADR-0018 amendment 2026-11-03) carries the device sync's one cause per VM: `server_report` gate, token-gated, strict V1 JSON up to `VIRTUSPHERE_DEVICE_SYNC_CAUSE_MAX_BODY_BYTES` (64 KiB, else 413) with `schema_version`, 32-hex `run_id`, boolean `complete` and at most 500 entries `{vm_id, rollout_revision, code}` from `VIRTUSPHERE_DEVICE_SYNC_CAUSES` (`lib/device_sync_cause_constants.php`, mirror `$script:VsDeviceCauseCodes`); unknown fields, numeric strings, unknown codes and a repeated `vm_id` answer 400 with a closed token. Display reports decide the revision fence per entry (ADR-0043 Amendment 2): the same pure `mecm_rollout_fence_revision_current()`, but a refused entry is counted as `stale` (revision not current, or the VM is off the device list) or `unknown_vm` (VM gone) in a 200 response, written nowhere and never audited; the 409 rule stays with callbacks that write `deploy_vms`. `complete = true` replaces the causes of other runs, `complete = false` only upserts, an identical replay answers `deduplicated: true`. The response is `{success, schema_version, run_id, complete, accepted, stale, unknown_vm, deduplicated}`. It never writes `deploy_vms` and emits no per-report audit row.

## A68 deploy_vm_touch.php admits one exact ESXi attempt per VM

- The new JSON-only POST keeps the existing machine-IP allowlist and adds no token, nonce, worker ownership or MAC-result contract. Its closed request is `{job_id, vm_id, attempt, generation, phase}`; exact success echoes those fields plus `success: true`. The active job, current attempt/runtime generation, persisted mission scope and playbook phase must all match before the journal row is marked. Refusal is closed 4xx (`400` malformed, `405` method, `409` stale/scope/phase, `413` oversized). The marker proves an authorized access attempt, not a successful ESXi mutation; the Ansible client must receive the exact acknowledgement before the matching VM's first `guest_info`. It writes no `deploy_vms` field and does not alter existing machine status or MAC-import wire contracts.

## A69 Every machine IP gate names its caller role; an entry admits only its role's endpoints

- Migration 0063 adds `deploy_accessToWebAPI.role` (`mecm_server`, `ansible_host`, `client`, or NULL). `lib/machine_api_roles.php` owns the role set and `VIRTUSPHERE_MACHINE_API_GATE_ROLES`, the one map from gate to admitted roles: Ansible host for `db_importMAC.php` and `deploy_vm_touch.php`; MECM server for `getDeviceList`, `updateDevice`/`reportMembership`, `mecm_packages.php`, `heartbeat`, `reportRun` and `reportDeviceCauses`; client for `getDeviceInfos`, `reportPhase`, `mecm_client_ack.php` and `reportPackageRun`. `machine_api_ip_allowed($db, $ip, $gate)` requires the gate key; `MachineApiRoleContractTest` derives the gates from the endpoint files and fails on a call without a key or with an unknown one.
- An entry without a role keeps opening every gate until an administrator assigns one; a role is never inferred. System status and the settings page count such entries. A role mismatch answers the unchanged legacy 403 body; only the throttled `machine_api.access_denied` audit row adds the closed `reason` (`ip_not_allowlisted` or `ip_role_not_permitted`). The throttle is keyed by IP and closed cause, so a change of cause writes its row at once; a refusal without a cause stays on the IP-only scope. The MAC-based client paths are untouched on purpose (ADR-0035 Amendment 2). One IP may hold one entry per role; an entry without a role blocks a second entry for that IP.
