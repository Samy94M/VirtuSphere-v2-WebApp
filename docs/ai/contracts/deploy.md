# VirtuSphere deploy contracts

Read the sections relevant to the current change. Paths below are relative to Docker/WebAPI unless they already name a repository directory. Forbidden patterns remain in GROK.md section 1; these are the constructive implementation contracts.

## A41 ESXi datacenter, datastore, portgroup and VM names are raw, case-sensitive identifiers. lib/esx

- ESXi datacenter, datastore, portgroup and VM names are raw, case-sensitive identifiers. `lib/esxi_object_names.php` owns supported-name validation and exact comparison; its folded key is diagnostic only and must never select an object, capacity value or callback target. Inventory name semantics, freshness and last observation are per kind. Datacenter derivation accepts exactly one supported semantics-2 name through the inclusive bound in `VIRTUSPHERE_ESXI_DATACENTER_DERIVATION_MAX_AGE_SECONDS`; an explicit mission value bypasses derivation.

## A42 Network validity lives in lib/vm_network_contract.php; DB scope, writer locking and active-job

- Network validity lives in `lib/vm_network_contract.php`; DB scope, writer locking and active-job checks live in `lib/repo/vm_network.php`. All interface writers preserve effective MACs and validate the proposed versioned fingerprint. New MAC assignments in editor and callback use `virtusphere_mac_assignment_existing_owners()` for one normalized, locking/current-read owner query. Editor writers take locks in Mission -> active Job -> Runtime -> VM -> Interfaces order; `db_importMAC.php` holds the same Runtime singleton before planning. Unchanged legacy assignments remain editable, and existing duplicate rows are not automatically repaired; a newly introduced duplicate is rejected. No MAC index or registry is added. General ambiguity groups the exact stored VLAN bytes, without trimming; empty detection remains trim-aware. Mission-WDS changes use the same Mission -> active Job lock path and are rejected during `running`/`cancelling`, while queued jobs remain editable for the worker recheck. General empty/exact-duplicate VLAN mappings block Create, Full, Powercycle and Export and warn for Start/Autostart. The separate exact WDS rule blocks Full/Powercycle/Export and warns for Create/Start/Autostart. Mode decisions derive from the playbook sequence, not another list.

## A43 Queue and stagger paths lock the mission, materialize the explicit selection (empty means all),

- Queue and stagger paths lock the mission, materialize the explicit selection (empty means all), run general and WDS gates, and insert in one transaction. The worker reuses the same aggregator after claim and before upload/SSH; an explicit ID that disappeared stays a blocked ID and never widens the scope. Per-VM canonical progress is mandatory. The bounded `network_preflight` result and terminal `failed/configuration_blocked` transition share one owner/status CAS; if cancellation wins, the job is `cancelled` without that result and the detail must say that no remote step started. Retry recomputes the current scope and applies precedence remote execution, identity, network, external prerequisites; it never widens a partial result to already successful VMs.

## A44 Every long-running CLI process this product makes PID 1 installs the shared stop handler from l

- Every long-running CLI process this product makes PID 1 installs the shared stop handler from `lib/worker_stop_signal.php` (ADR-0042), and it handles SIGQUIT as well as TERM/INT. Two measured facts make that mandatory: PID 1 ignores any signal it has no handler for, because the kernel applies no default action there, and this image inherits `STOPSIGNAL SIGQUIT` from `php:*-fpm`. Without it `docker stop` sat out its whole grace and SIGKILLed the worker mid-playbook (30.4 s, exit 137, versus 0.4 s and exit 0 after). Never keep a second signal list, never wrap a container command in a shell (the shell becomes PID 1 and forwards nothing), and never let an idle loop wait in an uninterruptible `sleep()` — use `worker_idle_wait()`.

## A45 The supervised process shape (ADR-0042) never starts a second child before waitpid confirms the

- The supervised process shape (ADR-0042) never starts a second child before `waitpid` confirms the old one is gone, and a child that survives TERM and KILL ends in `manual`, never in a replacement: a second process would run the same job twice and create the same VM twice. Its restart decision reads the child's liveness FILE and never the database, because a worker sitting out a database outage is healthy by explicit decision. Compose keeps starting the worker; the supervised shape is `docker-compose.supervisor.yml` plus an audited contract switch, and the snapshot fails closed to `degraded` while shape and stored contract disagree.

## A46 Creating VMs is one worker-driven unit per VM (ADR-0041), never one call over a loop. The queue

- Creating VMs is one worker-driven unit per VM (ADR-0041), never one call over a loop. The queue materializes one durable `deploy_create_vm_results` row per VM in the job's own transaction, ordered by `vm_name, id`; position is the identity a portal, a log line and a retry share. Create is not a step of `ansible_remote_steps()`: the worker drives Prepare/Launch/Status/Cleanup per unit, starts exactly one `vmware_guest` call with `async`/`poll: 0`, and polls the job id in the DERIVED `create.vm.<position>/async` directory rather than a second stored copy. Terminality is the job id plus the live identity read back, never the launch result file, and never the module's verdict: `async_status` answers a vanished id with `finished` and no `failed`, so the decision hangs off the status file. The next unit starts only when no row is `prepared`, `running` or `uncertain`, read from the rows and not from process memory. `uncertain` is not a softer `failed`; it stops the job, blocks retry (`retry_create_unresolved`), and is lifted only by the release whose evidence is an inventory pull strictly newer than both job and unit with neither name nor stored UUID present. `accounts.yml` leaves the Ansible host at every job end (K21): a removal counts only with exit 0 and its state line (`removed` or `absent`), a leftover is removed by a later contact only on the target recorded in its row (host, port, pinned host key), and a status query outside the job holds a lease on its row; only the async state stays, and the async directory of an unresolved unit is never deleted. Never add a second create path or a name-based recreate. An existing own VM is aligned only while it is powered off (DF-E1): otherwise the unit is verified and concluded `unchanged` without a launch (`prepared -> succeeded`, the success commit restricted to that outcome), and the launch rechecks the power state before its one mutation (`vm_not_powered_off`, never stored as a failure).

## A47 Preflight findings are bounded in one owner, lib/deploy_preflight_bounds.php, and only for pres

- Preflight findings are bounded in one owner, `lib/deploy_preflight_bounds.php`, and only for presentation or storage. A bounded list carries the complete `total` plus what it omitted, candidate groups add `candidate_total`/`candidate_omitted_count`, and selection runs on the canonical total order that ends in binary comparisons of the exact stored bytes. An encoded island above `VIRTUSPHERE_DEPLOY_PREFLIGHT_JSON_MAX_BYTES` loses entries from the END of that order and sets `truncated_by_bytes`; the stored worker result is bounded the same way and never refused, because throwing there labels a `configuration_blocked` job `execution_failed`. `VIRTUSPHERE_DEPLOY_JOB_SCOPE_MAX_VMS` and `VIRTUSPHERE_DEPLOY_JOB_SCOPE_MAX_INTERFACES_PER_VM` cap one job's scope before any remote work, because above them a legal V2 callback can exceed its 1 MiB bound after the playbook already created the VMs. `virtusphere_bounded_utf8_bytes()` is the one UTF-8 safe byte limiter.

## A48 MAC callback V2 is strict and additive: exact VM/WDS resolution, export-capable mode, active ru

- MAC callback V2 is strict and additive: exact VM/WDS resolution, export-capable mode, active `running`/`cancelling` status, current attempt/runtime generation and the applicable current remote export handle under the Mission -> Job -> Runtime -> Handle -> VM -> Interfaces lock order. Its fingerprint includes the sorted expected VM IDs plus sorted normalized semantic rows with multiplicity; key/list order and allowlisted diagnostic metadata or free error text do not change it. Callback expectations have their own playbook-derived registry, separate from remote-mode activation. Only a semantically identical replay of that same active execution is 200/no-op; different, unreadable or terminal duplicates are 409. V1 stays historically readable. Do not change the request envelope, legacy error meanings or the five machine status strings.
- For modes expecting a MAC result, worker marking skips VMs with a stored nonempty ResourceID. Successful unchanged comparisons and first MACs of a bound VM (empty stored MAC, K3 decision (b)) remain in `successful_vm_ids`, so conclusion and selective failure preserve lifecycle, MECM state, pickup flag and pending/watch timestamps. Missing/failed MAC evidence uses the existing failure contract; K15 below applies the same evidence-based journal rule to failure, cancellation, reaper and sweep.

## A49 Failure convergence uses one durable per-job, per-VM prestate and evidence journal

- Migration 0060 stores immutable lifecycle/MECM prestate and the job's per-VM marking, ESXi-touch and Create-launch-intent evidence in `deploy_job_vm_states`. Claims and the compatibility mark API capture before a VM write; `start` and `autostart` may capture but never change lifecycle or MECM. A job can change only VMs in its exact mission scope and current execution generation. The sweep resolves the latest journal owner by durable row id. A VM with no journal, or a journal from an older generation, is not repaired by inference.
- Worker failure, cancellation, heartbeat reaper and convergence sweep use the same evidence decision. A lifecycle bracket that was marked but has no confirmed ESXi attempt restores both saved values. A known per-VM ESXi attempt fails only that VM; `successful_vm_ids` remain authoritative and are never repainted. Create `pending` and `prepared` without launch intent mean no launch; `prepared` with intent, `running` and `uncertain` stay unknown; a completed unit with a known mutating async job can fail that VM, while `unchanged` and `skipped` restore.
- `powercycle` and `export` durably admit one VM immediately before that VM's first `guest_info`. The Ansible client requires the exact job/VM/attempt/generation/phase response before contacting ESXi; there is no selection-wide marker loop and no ESXi call after a refused or missing acknowledgement. The marker proves authorization of an access attempt, not a successful mutation. Query errors remain per-VM callback evidence.
- Create writes a durable launch intent under its original owner fence before the one async launch. A retry that finds the intent discovers the existing async job and never launches a second one. Only a definitive host-identity refusal or module `rejected` result before module start clears it under the same fence. Do not convert the crash gap, `running`, or `uncertain` into failed or untouched.

## A50 UUID-addressed jobs freeze runnable and skipped VMs in one queue-scope owner

- repo_deploy_mode_vm_selection() expands an unmarked empty selection (internal callers; the portal form blocks an explicitly emptied one as `selection_empty`) to the current whole mission first, then omits rows with an empty bound vm_instance_uuid only when the selected playbook sequence addresses existing VMs (start, export, powercycle, autostart). Create-capable create and full remain responsible for establishing the binding. Queue, schedule preview and stagger paths all use this resolver; preview and each stagger slot include only eligible VMs, while skipped IDs remain separate payload diagnostics.
- The pair vm_ids=[] and nonempty skipped_vm_ids means an explicit all-skipped scope. It must never be widened by network preflight, artifact preparation, callback, create fence or journal helpers that historically interpret empty vm_ids as the whole mission. Claim does not capture skipped VMs; failure, cancellation, reaper and restore paths do not mark or repair them. Do not pass skipped IDs as MAC results or change the existing MAC result envelope.

## A51 A VM binding records the access and access target that proved it; Create on another host warns and asks for confirmation

- Migration 0061 adds `deploy_vms.vm_bound_credential_id` and `vm_bound_esxi_host`. The create success commit and the MAC export's identity write set both from the job's ESXi access in the same statement that binds or confirms the instance UUID; the host is a snapshot of the access target at that moment, so a later retargeted access is still recognized. NULL means unknown and never warns. `repo_vm_create_host_moves()` (`lib/repo/vm_identity.php`) is the one derivation for create-capable modes: a bound VM in scope whose recorded host differs (case-insensitive, trailing dot ignored) from the selected access target. Its consumers are the queue warning, the POST confirmation step that reuses the schedule preview form (`confirmed=1`), the retry evaluation and its confirmation, and the job log's visible note; `deploy_host_move_message()` is the one sentence. It is never a blocker and never changes the Create identity contract (FM-E1).
