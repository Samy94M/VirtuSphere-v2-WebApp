# ADR-0021: Backup Status Channel and Mission Transfer Format

Date: 2026-07-09
Status: Accepted

## Context

Backups run as a host cron (`scripts/backup.sh`, ADR-0017) and are invisible to the portal: an admin only learns a backup failed by reading a log on the host. At the same time there was no supported way to move a single mission between environments (lab to production, or between customer sites) without hand-copying rows.

Two needs, one package:

1. Surface backup health in the portal without giving the web tier access to the dumps. The dumps and the config tar contain secrets (`.env` with the DB root password, encrypted credentials), so the PHP container must never be able to read them.
2. A portable, reviewable mission export/import that is explicitly *not* a backup/restore path and never carries identity or MAC state across environments.

## Decision

**Backup status channel.** `backup.sh` appends one JSON line per run to `Docker/backups/status/backup-status.jsonl` (`ts` as Unix epoch, `status`, sizes, `duration_s`, `keep`, `disk_free_pct/bytes`, `error`), truncated to the newest 90 lines, guarded by `flock`. Only this `status/` subdirectory is bind-mounted read-only into the PHP container (`/var/backups/virtusphere-status:ro`) — never the dumps or the config tar. A single reader (`lib/backup_status.php`) derives the state `ok | failed | stale | disk_low | unknown` (severity `failed > stale > disk_low`) and feeds the settings card, an admin-only dashboard banner and an informative `backup` field on `health.php`. The reader is fail-soft: a missing mount, empty file or half-written trailing line yields `unknown`, never a fatal. There is deliberately **no web restore and no dump download**; disaster recovery stays the documented CLI path.

**Mission transfer format.** `lib/mission_transfer.php` exports one mission as versioned JSON (`format_version` constant shared by export and import): mission fields, VMs, interfaces **without MAC**, disks and package references by name. Import re-creates the mission under a new name in one transaction, reusing the portal's own validators and write helpers (`repo_validate_vm_payload`, `repo_replace_interfaces/disks/packages`); VMs come in fresh (Registered / not_ready) exactly like a template clone. Import is a two-step flow — a dry-run preview report held server-side in the session with a 10-minute TTL, then a confirmed write. The report carries counts and the export timestamp, resolved vs missing packages, missing VLANs, global VM-name conflicts (with the mission that holds each name), VM names repeated inside the file, an invalid target name, and every field the portal's own validators reject in the mission block or in a VM. Everything except a missing package **blocks** the import (SCCM device names are global; missing packages are a warning and are skipped). A problem is a report field, never an exception: the preview must stay renderable for any document that can be read at all, because a preview that cannot render says nothing at all. Only an unreadable document (wrong `format_version`, malformed top-level structure) throws, as a typed `MissionTransferDocumentException` carrying a localized message. The report carries two block flags on purpose: `blocked` is the single predicate the write refuses on, `blocked_in_file` is the subset the confirm form cannot fix and is the only thing that disables its button. A name problem is deliberately outside that subset, because the field that fixes it sits under the message and the confirm re-runs the whole analysis against the name actually typed; disabling there would state an instruction the operator cannot carry out. The write refuses a blocked report again inside `mission_import()`: the preview is a report, not the security boundary. CSV list export (`lib/portal_export.php`) is a convenience only: semicolon delimiter, UTF-8 BOM, formula-injection guard.

**One canonical reading of the document.** `lib/mission_transfer_document.php` canonicalizes the decoded payload once, and the report, the field validation and the transaction all read that result. The preview and the write used to read the same file in two different ways: the report counted `(array)` casts while the write projected the transfer field lists, so `interfaces: "oops"` counted as one interface and produced no finding while the write built an empty DHCP interface, `disks: "oops"` counted as one disk and wrote none, a package reference without a name disappeared, and an extra `interfaces[*].mac` blocked a preview over a value the import deliberately drops. Container shape is decided by `array_is_list()`, never by a cast; the field lists (`VIRTUSPHERE_MISSION_TRANSFER_MISSION_FIELDS`, `_INTERFACE_FIELDS`, `_DISK_FIELDS`, `_PACKAGE_FIELDS`, `REPO_MISSION_COPYABLE_COLUMNS`, `REPO_VM_COLUMNS`) are the only projection, and both directions of the format walk them. Anything outside them (MAC, ids, MECM and lifecycle state, a field a later version adds) is unknown: it can neither be written nor produce a finding. A known writable field with the wrong type is a positioned in-file finding and blocks; `mission_status` is exempt because the import always replaces it, and `mission_name` only feeds the editable target field. `exported_at` is display metadata: unusable values become empty and the preview omits the row rather than printing file content under a timestamp heading. Counts are formed from canonical entries only, so for any report that is not blocked the counts are exactly the units the transaction writes.

**Session hand-off, upload layer and diagnosis.** There is exactly one active import per session; a new upload replaces the previous one. `lib/mission_import_portal.php` answers what a request's token means with one closed status (`valid | expired | mismatch | missing | invalid`) that both the GET preview and the confirm POST read. Only a request that OWNS the hand-off may delete it: a mismatch is about a different upload, and the earlier duplicated condition deleted it anyway, so opening the stale link of upload A destroyed the still valid preview of upload B in the same session. The TTL boundary is inclusive (age equal to the TTL is still valid). Cancel is a link and deliberately does not delete anything: the state ages out with the TTL or is replaced by the next upload, and Back inside that window shows the same preview again; a dead hand-off is swept silently on any further render of the page. Uploads pass three limits above the app's own `VIRTUSPHERE_MISSION_IMPORT_MAX_BYTES`: `upload_max_filesize`, `post_max_size` and nginx `client_max_body_size`, in that order, so the app's localized size message is the one the operator sees. The form renders `MAX_FILE_SIZE` from the same constant as early detection only; the server compares the reported size itself, because a client controls that field. Above `post_max_size` or the nginx limit no localized answer is possible at all, since PHP no longer sees action, CSRF token or payload; that infrastructure cut-off is named in the runbook instead of being promised away. Every `UPLOAD_ERR_*` code is classified separately rather than folded into "no file chosen". Expected outcomes (file, name, structure, TTL, stale token, size) are localized and write **no** log line anywhere; an unexpected caught fault yields an error reference plus exactly one `error_log()` line naming phase, reference and exception class or upload code, with no payload, token, file name, temp path or session content. A successful import keeps writing exactly one existing `missions` audit row; there is no audit-on-failure convention, no new category, column, migration or job-log source.

## Consequences

- Backup health is visible where admins already work, with zero new secret exposure: the web tier sees only metadata.
- The status channel is metadata and is intentionally not itself backed up; the inventory cache is self-healing and also excluded (see the coverage table in `docs/operations/backup.md`).
- Export/import is a transfer tool, not a recovery tool. It never writes primary keys, MAC addresses, MECM ids or workflow state from a file, so it cannot resurrect a decommissioned VM's identity.
- New compose mount (`Docker/backups/status`) must exist in every environment; deploy docs updated. The directory is created by `backup.sh`; before the first run the card shows `unknown`, which is correct.
